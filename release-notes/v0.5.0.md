Fifth release of nia-edge, the client of Nia. It is a pre-release. The agent's MCP servers hosted by their vendor (GitHub, Notion…) are reached through nia-edge, which keeps their token: the agent never holds it.

**New**
- **Vendor-hosted MCP servers.** `nia-edge mcp remote add <name> -url <https URL>` (token on standard input) keeps the token in nia-edge's state file. The agent reaches the server at `http://127.0.0.1:8787/remote/<name>/mcp`, without a token. Nia pins the vendor's tools for the tenant: a changed or new tool is hidden until an admin approves it. A call runs only against a release of the model path or of the agent's hooks, and a secret in an answer is redacted.
- **Sign in instead of pasting a token.** `nia-edge mcp remote login <name> -url <URL>` follows the MCP authorization specification:
  - discovery from the server's 401;
  - registration through nia-edge's client document served by Nia, dynamic registration, or `-client-id`;
  - PKCE S256 required, `state` checked, the server's URL as resource.
  The browser can be on another machine: paste the address it was sent to. Access and refresh tokens stay in the state file; nia-edge renews them.
- **Resources and prompts.** They are relayed too. Reading one taints the run, as a tool result does.
- **Hermes and OpenClaw.** `install/mcp-linux.sh remote|login|remote-remove` points their configuration at nia-edge and keeps the token off the agent.

**Upgrade from 0.4.0**

`sudo sh update-linux.sh v0.5.0`. Signing in with the client document needs Nia 2026-11-19 or later; without it, nia-edge registers itself dynamically or takes `-client-id`.
